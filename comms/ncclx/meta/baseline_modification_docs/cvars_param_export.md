# CVAR parameter-registry visibility

## Decision

Do not restore `NCCL_PARAM_COMPILER_EXPORT_SYMBOL` as a standalone baseline port. Default visibility can make the parameter accessors available in `.dynsym`, but it does not make registry operations share one process-wide state.

Revisit registry sharing only when a behavioral two-DSO test demonstrates duplication and the proposed fix makes registration, lookup, and removal cross the DSO boundary. Symbol-table counts are supporting evidence, not acceptance criteria.

## Scope of the row

The parameter-registry change spans eight baseline files rather than only `src/misc/param.cc` and `src/param/param_registry.cc`:

- `src/misc/param.cc`
- `src/param/param.cc`
- `src/param/param_registry.cc`
- `src/param/ncclparam.cc`
- `src/param/c_api.cc`
- `src/include/param/param.h`
- `src/include/param/utils.h`
- `src/include/param/param_registry.h`

Most apparent drift in this area comes from upstream formatting, signatures, and features already present in the newer baseline. Compare behavior and symbols before replaying a raw patch.

## Why visibility matters

The fbcode build uses hidden default visibility. A version script can filter or version a symbol that already reached `.dynsym`, but it cannot promote a hidden definition into the dynamic symbol table. If a plugin must resolve a parameter accessor by name, the definition needs an explicit export mechanism.

This is why `NCCL_PARAM_COMPILER_EXPORT_SYMBOL` is not decorative. Adding it exposes the accessor and the helpers generated by `DEFINE_NCCL_PARAM`.

## Why visibility is insufficient

`ncclParamRegistry::add`, `find`, and `remove` are defined in the same translation unit as `ncclParamRegistryInstance`. With normal Clang optimization and `-fno-semantic-interposition`, those methods can inline the accessor and address the translation-unit-local static directly. The externally visible accessor can therefore return one state while the registry methods continue using another.

The standalone shared library also links with `-Bsymbolic`, which binds internal references locally regardless of default visibility. Static NCCLX archives embedded in another DSO do not inherit that linker flag, but same-translation-unit optimization still applies.

A viable fix must force all registry operations through one definition. Candidate mechanisms include moving the accessor to a separate translation unit, preventing inlining and enabling semantic interposition, or owning the registry in one shared DSO. Each mechanism needs artifact-level verification; its source spelling is not proof.

## Required verification

Use a self-contained fixture with two independently linked DSOs. Each DSO must contain the NCCLX parameter-registry objects, and the full symbol table must confirm that the fixture is not vacuously using one shared copy.

The behavioral check must:

1. Load both DSOs in the same order used by the real process.
2. Register a unique parameter through DSO A.
3. Find and remove that parameter through DSO B.
4. Verify missing-key and duplicate-registration behavior from both sides.
5. Repeat with the actual linker modes used by the standalone library and by statically embedded consumers.

Also disassemble `ncclParamRegistry::add`, `find`, and `remove` in every relevant artifact. They must call or otherwise resolve through the intended shared accessor instead of loading a local `ncclParamRegistryInstance::state` directly.

Comparing accessor addresses is useful but not sufficient. Two DSOs can report the same exported accessor address while their inlined registry methods still address private local statics. The cross-DSO registration/lookup behavior is the deciding signal.

## Diagnostics that do not answer the question

- `nm -D` shows whether a symbol is dynamically visible, not whether internal operations use it.
- An accessor-address comparison does not exercise `add`, `find`, or `remove`.
- Source search for external references misses symbol interposition by construction.
- A failed build of one consumer target only rules out measuring that exact target at that revision. It does not prove that no other DSO embeds NCCLX, that no plugin resolves the helpers, or that the topology is unmeasurable.

For a real consumer, inventory the loaded objects and their `DT_NEEDED` entries, inspect link maps or full symbols to identify statically embedded NCCLX copies, and then run the behavioral test in that topology. Use `RTLD_NOLOAD` when observing an existing process so the probe does not change load order or visibility.

## Environment-plugin alternative

The upstream environment-plugin path is a possible way to serve NCCLX CVAR values without baseline interception, but `ncclGetEnvImpl` is not a drop-in `getEnv` callback.

`ncclEnv_v2_t` contains a name and three operations:

- `init`, which receives the NCCL version and logger;
- `finalize`;
- `getEnv`, which returns `nullptr` when a key is absent.

The plugin owns the returned string storage. A value must remain valid until `finalize` or until the next `getEnv` call for the same key.

Once NCCL loads an external environment plugin, that plugin is the sole resolver. A `nullptr` result from its `getEnv` callback is final; NCCL does not retry the internal `getenv`-backed plugin. An adapter that only translates an unknown Meta CVAR to `nullptr` would therefore suppress valid baseline-only process-environment keys such as `NCCL_PARAM_DUMP_ALL`, which is not represented in the current Meta CVAR maps.

The current `ncclGetEnvImpl` throws `std::runtime_error` for an unknown key, returns `nullptr` for an explicitly empty string CVAR, and uses thread-local cached storage for numeric conversions. An adapter must define precedence explicitly: return the registered Meta CVAR when the key is represented in the Meta maps, preserve the mapped empty-string semantics, otherwise fall back to `std::getenv`, and return `nullptr` only when neither source defines the key. It must also preserve the required pointer lifetime across threads and implement safe initialization and finalization. Dedicated tests must cover Meta-over-environment precedence, mapped empty strings, baseline-only environment keys in both set and unset states, numeric storage lifetime, and concurrent access before replacing the existing baseline adapter.

## Adjacent changes outside this decision

Linker version-script differences affect exported CTran, PRiMS, logging, and exception-tracing symbols independently of parameter-registry sharing. Keep those changes with their owning rows.

Likewise, do not reintroduce private logger conversion helpers when the baseline already routes through the shared logging implementation.

## Revert checklist

This decision adds no baseline behavior. If a future registry-sharing implementation lands, its revert must remove the mechanism and its behavioral two-DSO test together; retaining export annotations without the behavioral guarantee recreates the ambiguity documented here.
